## QA 소스 기준

- 작업 기준은 `QA Reports`가 아니라 하단의 `QA Issues` 데이터베이스다.
- `Status`가 `Open`인 항목뿐 아니라 status가 비어 있는 항목도 수정 대상이다.
- status 옵션은 현재 `Open`, `Resolved`, `보류`를 사용한다.
- 코드로 확정 처리한 항목은 Notion status를 `Resolved`로 변경한다.
- 피그마 수치, 이미지 에셋, 정확한 디자인 값이 필요한 항목은 코드에 `TODO(QA)`를 남기고 Notion status를 `보류`로 변경한다.
- 약관 및 개인정보 처리방침은 이미지로 넣기로 했으므로 코드 수정 대상에서 제외한다.

## Figma 값 처리

- Figma 접근이 불안정하거나 정확한 수치를 확인할 수 없으면 임의로 값을 맞추지 않는다.
- 수치가 필요한 위치에 `TODO(QA)` 주석을 남긴다.
- 주석은 사용자가 피그마에서 값을 찾아 바로 기입할 수 있도록 어떤 수치가 필요한지 구체적으로 적는다.
- 예시:

```tsx
{/* TODO(QA): Figma ReadingDetails_QuizCorrect/Incorrect 기준 퀴즈 제목과 정답/오답 태그 사이 간격 수치 확인 필요 */}
<Spacer num={16} />
```

## 브랜치 규칙

- 브랜치명에 `codex`를 넣지 않는다.
- 일반적인 브랜치명을 사용한다.
- 예시:
  - `fix/settings-qa`
  - `fix/my-page-qa`
  - `fix/reading-detail-qa`
- 새 QA 묶음을 시작할 때는 가능한 `develop` 기준으로 새 브랜치를 만든다.

## 커밋 규칙

- 커밋은 한 번에 몰아서 하지 않는다.
- 파일별 또는 기능/범위별로 나눠 커밋한다.
- 사용자가 `커밋해줘`라고 요청했을 때 커밋한다.
- 사용자가 직접 푸시한다고 했으므로 푸시는 하지 않는다.
- 커밋 메시지는 한국어 요약을 포함해 간결하게 작성한다.
- 예시:
  - `fix(my-page): 읽은 글 카드 QA 반영`
  - `fix(reading-detail): 퀴즈 결과 간격 QA 주석 추가`

## PR 요청 해석

- 사용자가 `PR 만들어줘`, `PR 채워줘`, `PR 템플릿 만들어줘`라고 하면 실제 GitHub PR 생성이 아니라 복붙 가능한 PR 제목과 본문을 코드블록으로 제공한다.
- PR 본문은 프로젝트 PR 템플릿 형식을 따른다.
- PR 문장은 반말 대화체가 아니라 짧은 명사형/서술형으로 끝낸다.
- 선호 표현:
  - `수정`
  - `반영`
  - `추가`
  - `제거`
- PR 제목과 스쿼시 제목도 함께 제안한다.

## `다음 작업 해줘` 해석

- Notion QA Issues에서 다음 `Open` 또는 status가 비어 있는 항목을 확인한다.
- 적절한 화면/컴포넌트 단위로 묶어 새 브랜치를 만든다.
- 코드로 가능한 항목은 바로 수정한다.
- 수치나 에셋이 필요한 항목은 코드에 `TODO(QA)`를 남긴다.
- 커밋은 사용자가 별도로 요청하면 수행한다.
- 완료 후 어떤 QA를 처리했는지, 어떤 항목이 `보류` 대상인지 정리한다.

## Notion 업데이트 기준

- 작업 후 사용자가 노션 업데이트를 요청하면 status를 변경한다.
- 확정 완료 항목: `Resolved`
- 수치/에셋/디자인 확인 필요 항목: `보류`
- 아직 작업하지 않았거나 확인이 필요한 항목: `Open` 또는 빈 상태 유지
